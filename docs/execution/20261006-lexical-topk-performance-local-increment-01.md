# Bounded lexical top-k performance increment, 2026-10-06

One equivalent top-k selection change is adopted in `retrieval/lexical.py`: `heapq.nsmallest` uses the same `(-score, chunk_id)` key instead of fully sorting every row. The measured improvement is **whole warmed lexical search on 4,096 synthetic rows, k=50**, not page or backend end-to-end performance.

| --- | ---: | ---: | ---: | ---: |
| Ascending IDs | 30 | 1.43705 → 0.80020 | 1.679235 → 1.003915 | -40.22% |
| Deterministically shuffled IDs | 30 | 1.57475 → 0.79355 | 1.803630 → 1.062895 | -41.07% |

All **148 planned timed attempts succeeded**, with zero failure or unstarted attempts. The 72 paired queries (60 measured warm, two first-query pairs and ten warmup pairs) returned identical dictionaries, exact float scores and ordered IDs. The existing six pure retrieval-cache unit tests also pass, including 920 reference BM25 comparisons across queries, visibility subsets and k values. Unicode casefolding, positive/zero-score ties, empty data, k beyond membership and nested input/output copy isolation were checked. No speed threshold was used as a test assertion. Five existing queries, including empty and absent terms, were included; every per-query/layout warm median improved in this run.

Cold index construction is separate and unchanged by the implementation: ascending reference/candidate took 34.1101/33.1238 ms; shuffled took 34.3874/37.2105 ms. There is only one construction per arm/layout in one process, not a cold interpreter or OS-cache experiment, and no cold-start improvement is claimed. First queries took 1.9771/1.0546 ms and 1.7311/1.3911 ms respectively. Warm percentiles use linear interpolation at (n−1)×0.95. The approximately 0.7 ms p95 savings are descriptive local measurements; they are not a 40% product speed claim or evidence that the page p95 target has been reached.
