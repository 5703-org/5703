## Findings that changed the implementation

The existing chat policy already combines dense retrieval and BM25 through reciprocal-rank fusion, then runs a pinned local cross-encoder. Before this change, reranking preserved every candidate regardless of its score. The generator had a programmatic refusal for an empty evidence set, but irrelevant nonempty evidence still reached the answering model. `conversation_preparer_v5` treated “Do you know what is rag” as an ordinary factual query with no ambiguity. The supplied screenshot establishes a topic substitution; it does not independently establish that a query rewriter produced the word “ragweed.”

The revised flow is:

```text
Learner message + prior learner turns
  -> bounded term understanding / explicit correction
  -> clarification, or standalone retrieval question
  -> existing dense + BM25 / RRF retrieval
  -> existing pinned learned reranker
  -> expanded-concept guard + model-specific relevance screen
  -> existing token-budget selection
  -> grounded generation and citation validation
```

`conversation/understanding.py` supplies a small, explicit English alias catalogue. Bare RAG asks for clarification. An explicit AI context expands it to retrieval-augmented generation; RAG1, recombination-activating genes and ragweed retain their biological meaning. Prior assistant guesses cannot establish the domain. An explicit correction creates a new retrieval question and does not reuse the old guessed answer's evidence. Unknown abbreviations and arbitrary misspellings remain outside this bounded resolver; this is not a general semantic query-understanding model.

`retrieval/relevance.py` screens expanded terms using word boundaries, preventing a prefix match such as RAG/ragweed from establishing relevance. Complementary passages can each cover one concept in a multi-concept question. The learned score threshold applies only to `cross-encoder/ms-marco-MiniLM-L6-v2` at commit `233902d25c440f23af6f7d6e94d2946bac0bee0a`. The provisional raw-logit threshold is **-4.0**. It was chosen after inspecting five positive and three negative development questions: positive top scores were at least 4.012; negative top scores were at most -8.997. Eight subsequent held-out examples check for obvious regressions. This small exercise does not calibrate a probability, establish an optimal cutoff or substitute for independently labelled retrieval evaluation. A different reranker receives the expanded-term guard only until its own threshold is validated.

New interactive requests freeze the relevance policy and requested device in their command. Rejected candidate IDs, reasons, raw scores and the accepted IDs remain in the request trace. At this initial checkpoint, knowledge-expanding follow-ups could not append old evidence that fresh retrieval had not reconfirmed. The current version instead validates membership and rescores a bounded fresh/prior union before screening. Direct restatements continue to reuse the prior answer's cited evidence. Formal E0/E1 retrieval remains unchanged, and old requests without the new fields keep their recorded device and relevance behavior. An all-rejected result produces a strict grounded refusal with no textbook citations and no answering-model call. General-model knowledge was not enabled at this initial checkpoint. The later explicit per-request mode has separate provenance and is documented in the integrated record; there is no automatic fallback.

## CPU portability and preservation

The earlier release identity included `embedding_device` in its recorded configuration and embedding signature. Editing a CUDA release in place would break that identity. Query execution now accepts a separate device override while keeping the stored configuration, vectors, model/tokenizer revisions, preprocessing and source identities intact. Rebuilding 10,594 vectors is unnecessary merely to run queries on another supported device.

`LOCAL_MODEL_DEVICE=auto` resolves an available CUDA device, then MPS, then CPU. Explicit `cpu`, `cuda`, `cuda:0`, `mps` and legacy `recorded` modes are available through application settings. Explicit unavailable accelerators fail visibly; a model load failure or out-of-memory error does not silently trigger another model or device. The request trace records requested and resolved devices. A mock-only corpus needs no optional Torch installation.

The portable Windows launcher accepts `-Device cpu` and no longer asserts that CUDA exists. A new `requirements-embeddings-cpu.lock` uses the official CPU wheel. Fresh `-Install` with `auto` chooses the CPU lock; explicit CUDA uses the retained CUDA lock. Existing installed accelerators remain usable with `auto` without reinstalling. The separate CPU-only verification directory does not replace the development environment. MPS selection has a unit test, not a physical Mac execution claim. CPU/GPU bitwise equivalence is not guaranteed by PyTorch; device choice is therefore recorded rather than hidden. [Official PyTorch reproducibility guidance](https://docs.pytorch.org/docs/stable/notes/randomness), [official version-specific CPU installation](https://pytorch.org/get-started/previous-versions/), [SentenceTransformers device API](https://www.sbert.net/docs/package_reference/sentence_transformer/model.html).
