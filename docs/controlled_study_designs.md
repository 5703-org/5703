# Controlled retrieval study preparation

Two immutable designs were prepared on 8 September 2026 for the full, pinned SciQ validation split. They complete the **configuration and paired-schedule preparation** for RET-10's `top_k` and embedding comparisons. Compatible judged qrels are still missing, so the full task remains `IMPLEMENTED_UNVERIFIED`. Neither design has executed a condition; relevance judgments, answer-quality results and human scores are absent. The separate fixed-chunking implementation and its evidence are tracked independently.

The retained nullable R0 pool belongs to the earlier v4 comparison release and is not compatible with the v5/fixed releases. Current source-span mappings support mechanical comparison, but do not supply relevance judgments or authorize reuse of incompatible labels. The unexecuted designs keep qrels absent; compatible source review or reannotation is required before a valid relevance measurement.

The public record is [preparation.json](../evidence/evaluation/ret10-design/preparation.json); [integrity-review.json](../evidence/evaluation/ret10-design/integrity-review.json) records a fresh replay of the existing comparison validator, exact private-file and canonical-design hashes, and full-ID identity checks. Both positive comparisons passed. Negative controls rejected different question IDs, a second changed answer-model factor, and R3 relabelled as frozen E1.

Each design contains all 1,000 unique validation IDs in original source order from SciQ revision `2c94ad3e1aafab77146f384e23536f97a4849815`. Each proposes 1,000 items per arm, or 2,000 paired conditions, with alternating arm order. These are proposed denominators, not completed runs. Errors and refusals must remain in any eventual results.

The immutable private files are `artifacts/evaluator-private/study-designs/ret10-full-validation-20260908/top_k.json` and `embedding.json`. They retain the full IDs, paired schedule, actual baseline release configuration and manifest. Public evidence contains only counts, hashes, configuration identities and prerequisites. The study adapter sends the exact question stem through the shared application answer service; gold answers, support and distractors remain evaluator-private. OpenQA includes all 1,000 rows. The three native duplicate-choice validation rows still block strict whole-split MCQ; the separate two-row technical rehearsal is not substituted here.

Both designs bind actual active v5 release `4f11bd70-a486-4d16-b216-78cfe499530a`, the same four official source hashes, unchanged processing/chunk identities, R0 with E1, the same prompt and response schema, disabled profile/history, scorer version and seed. The currently configured answer provider is **mock**, with its exact model settings frozen. A later live-answer study requires a new matched design with the new model identity. No live-quality result is implied by these prepared designs.

The alternate repository was resolved through the official Hugging Face API to revision `f52bf8ec8c7124536f0efb74aca902b2995e5bcd`. Its pinned [model configuration](https://huggingface.co/intfloat/e5-base-v2/resolve/f52bf8ec8c7124536f0efb74aca902b2995e5bcd/config.json), [tokenizer configuration](https://huggingface.co/intfloat/e5-base-v2/resolve/f52bf8ec8c7124536f0efb74aca902b2995e5bcd/tokenizer_config.json) and [pooling configuration](https://huggingface.co/intfloat/e5-base-v2/resolve/f52bf8ec8c7124536f0efb74aca902b2995e5bcd/1_Pooling/config.json) declare 768-dimensional output, `BertTokenizer`, a 512-token limit and mean pooling. Exact fetched bytes, URLs, time and hashes are preserved in [official-metadata/manifest.json](../evidence/evaluation/ret10-design/official-metadata/manifest.json). Only metadata was downloaded for this preparation.

Before embedding execution, acquire and hash the pinned model/tokenizer assets, check every unchanged baseline chunk against the actual alternate tokenizer without silent truncation or rechunking, and build a distinct complete 768-dimensional release over those exact chunk IDs. The proposed alternate release ID is explicitly null. Its actual ID and verified manifests must be frozen into a new immutable execution-ready design. Use an isolated comparison environment and leave the product's active pointer unchanged. Obtain actual source-span qrels and independent reviews before reporting retrieval relevance or semantic quality. No fabricated scores or assumed human judgments appear in either design.

The preparation helper is [prepare_ret10_studies.py](execution/prepare_ret10_studies.py). It refuses to overwrite the private study directory and reads the application database with PostgreSQL read-only transactions. It changes no runtime code, release, model weights or active configuration.
