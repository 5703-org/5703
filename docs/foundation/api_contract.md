# API and operator contract

All application routes are under `/api/v1`. Success is `{data,meta:{trace_id}}`; error is `{error:{code,message,details},meta:{trace_id}}`, with matching X-Request-Id. Authentication uses a bearer token returned at login, stored in browser sessionStorage and cleared at logout. Disabled users or stale token versions cannot access data. Another user's resource returns404; a learner's admin action returns403. [Runtime OpenAPI](../../contracts/openapi.json) now replaces the initial design export and is generated by `python -m scripts.verify.contracts --write`; typed frontend responses are generated and drift-checked from it. `contracts/models.py` and `contracts/http.py` define the current DTO/envelope authority. [SPEC.md](../../SPEC.md) is the actual-system entry point; table summaries below are subordinate to the executable schema.

The learner landing route is `/chat`. Only `{content,use_profile}` is accepted from the composer; choices, gold, history, owner and model fields are forbidden. Profile levels are beginner/intermediate/advanced; styles concise/detailed/socratic; initial language en; up to 20 self-reported topics of 200 characters each. An explicit invalid value is 422, while absent legacy policy gets a recorded intermediate fallback.

An answered ChatResponseV1 contains exactly schema_version, response_type, answer_text, short_answer, citations, refusal_reason, follow_up_questions, confidence. Example: `{schema_version:"chat_response_v1",response_type:"answer",answer_text:"Light energy is stored in sugars. [ev_001]",short_answer:"Chemical energy in sugars",citations:["ev_001"],refusal_reason:null,follow_up_questions:[],confidence:null}` is an authored fixture only and requires matching context. A refusal uses response_type refusal, useful answer_text, null short_answer/confidence, empty citations/follow-ups and a permitted reason. A provider error instead returns a failed job with a code such as PROVIDER_TIMEOUT and recovery guidance; it never masquerades as refusal.

Request states queued/processing/answered/clarification/refused/error/cancelled map to job states queued/running/retry_wait/succeeded/failed/cancelled. Polling returns only validated published answers. 409 covers session busy, stale revision, idempotency conflict and disallowed retry; 410 unavailable evidence; 413 oversize; 415 unsupported content; 422 invalid input/output schema; 503 dependency/configuration and 504 timeout. Errors include safe trace metadata, never raw credentials or private provider reasoning.

Administrative CLI equivalents: `app.cli migrate`, `seed-demo --confirm-dev`, account create/disable/reset-password, ingest --manifest, corpus-build --config, corpus-activate --release, corpus-rollback --release, job inspect/retry/recover, config create, feedback review, source revoke, cleanup dry-run/apply. Backup/restore use distinct confirmed targets. The tested command mapping and actual results are maintained in the runbook; initial design entries are not claims of implementation.
